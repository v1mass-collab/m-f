Q1. DOCKER – MULTI-CONTAINER APPLICATION (20 MARKS)
Aim:
To deploy a Digital Library Portal using WordPress as the frontend and MySQL as the backend with Docker containers, networking and persistent storage.

Step 1: Start Docker Desktop.

Open Docker Desktop and wait until Docker Engine is running.

Verify Docker:
docker --version
docker info


Step 2: Pull the required images.
docker pull mysql:8.0
docker pull wordpress:latest


Step 3: Create a custom Docker network.
docker network create library-network


Step 4: Create a persistent volume for MySQL.
docker volume create library-db-data


Step 5: Run the MySQL container.
docker run -d ^
--name library-db ^
--network library-network ^
-e MYSQL_ROOT_PASSWORD=root123 ^
-e MYSQL_DATABASE=library ^
-v library-db-data:/var/lib/mysql ^
--restart unless-stopped ^
mysql:8.0


Step 6: Run the WordPress container.
docker run -d ^
--name library-wordpress ^
--network library-network ^
-p 8080:80 ^
-e WORDPRESS_DB_HOST=library-db:3306 ^
-e WORDPRESS_DB_USER=root ^
-e WORDPRESS_DB_PASSWORD=root123 ^
-e WORDPRESS_DB_NAME=library ^
--restart unless-stopped ^
wordpress:latest


Step 7: Verify running containers.
docker ps


Both WordPress and MySQL containers should be running.

Step 8: Access WordPress.

Open the browser:
http://localhost:8080


Complete the WordPress installation.

Step 9: Demonstrate container recovery.

Stop MySQL:
docker stop library-db


Restart MySQL:
docker start library-db


Verify:
docker ps


Step 10: Demonstrate database persistence.

Remove the MySQL container:
docker rm -f library-db


Recreate it using the same volume:
docker run -d ^
--name library-db ^
--network library-network ^
-e MYSQL_ROOT_PASSWORD=root123 ^
-e MYSQL_DATABASE=library ^
-v library-db-data:/var/lib/mysql ^
--restart unless-stopped ^
mysql:8.0


The database files remain stored in the Docker volume.

Expected Output:
- WordPress website accessible at localhost:8080.
- MySQL and WordPress running in separate containers.
- Both containers communicating through a custom network.
- Database information preserved using a named volume.
- Containers can be restarted and recovered.
Scenario-Based Questions:

1. What happens if the MySQL container crashes while WordPress is running?

Answer: WordPress temporarily loses its database connection. Database operations fail until MySQL becomes available again. The restart policy helps restart the MySQL container after certain failures.

2. How can database information be recovered after container deletion?

Answer: Store database files in a Docker volume. Recreate the MySQL container using the same volume.

Command:
docker volume ls


3. Why is a custom Docker network required?

Answer:
- Allows containers to communicate.
- Provides container-name-based communication.
- Provides network isolation.
- Avoids depending on changing IP addresses.
4. How would you prevent unauthorized access to MySQL?

Answer:
- Use strong passwords.
- Do not expose port 3306 publicly.
- Use a private Docker network.
- Create database users with limited privileges.
- Allow only authorized containers to access the database.
5. How would you deploy five department websites using Docker?

Answer:
- Create five WordPress containers.
- Configure separate databases or separate databases/users in a shared MySQL server.
- Use persistent volumes.
- Configure different ports or a reverse proxy.
- Use Docker networking for communication.

Q3. KUBERNETES – CONTAINER DEPLOYMENT AND AUTO SCALING (20 MARKS)
Aim:
To containerize the actual Library Management Java application and execute it using Kubernetes.

Important:
The supplied Java application is a console program that prints a menu and exits. It is not a continuously running web service. Therefore, a Kubernetes Job is appropriate for running the actual repository application. The Deployment, Service and scaling requirements in the question need a long-running application.

A. Repository-specific execution

Step 1: Clone the repository.
git clone https://github.com/deepthisagar7/library-management.git


Step 2: Open the project folder.
cd library-management


Step 3: Build the application.
mvn clean package


Step 4: Create a Dockerfile.

Create a file named Dockerfile in the project root.
FROM eclipse-temurin:17-jdk

WORKDIR /app

COPY target/library-management-1.0-SNAPSHOT.jar app.jar

CMD ["java", "-cp", "app.jar", "com.library.LibraryManagement"]


Step 5: Build the Docker image.
docker build -t library-management .


Step 6: Run and test the Docker image.
docker run --rm library-management


Expected output:
Library Management System
1. Search Book
2. Issue Book
3. Return Book
4. Reserve Book


B. Kubernetes execution

Step 7: Start Minikube.
minikube start


Step 8: Load the Docker image into Minikube.
minikube image load library-management:latest


Step 9: Create a file named library-job.yaml.
apiVersion: batch/v1
kind: Job

metadata:
  name: library-job

spec:
  template:
    spec:
      containers:
        - name: library-container
          image: library-management:latest
          imagePullPolicy: IfNotPresent

      restartPolicy: Never


Step 10: Apply the Kubernetes Job.
kubectl apply -f library-job.yaml


Step 11: Verify the Job and pod.
kubectl get jobs
kubectl get pods


Step 12: View application output.
kubectl logs job/library-job


This demonstrates execution of the actual Java repository inside Kubernetes.

C. Commands for the Deployment requirements in the question

These commands demonstrate the required Kubernetes operations, but a working browser-accessible application requires converting the console program into a long-running web service first.

Step 13: Create a Deployment with two replicas.
kubectl create deployment library-deployment --image=library-management:latest --replicas=2


Step 14: Expose the application.
kubectl expose deployment library-deployment --type=NodePort --port=80 --target-port=8080


Note: The current Java application does not listen on port 8080, so this Service will not provide working browser access.

Step 15: Scale from two to five replicas.
kubectl scale deployment library-deployment --replicas=5


Step 16: Check pods.
kubectl get pods


Step 17: Demonstrate pod recreation.
kubectl delete pod <pod-name>


Check again:
kubectl get pods


The Deployment controller attempts to maintain five replicas.

Step 18: Demonstrate rolling update.
kubectl set image deployment/library-deployment library-container=library-management:v2


Step 19: Check rollout status.
kubectl rollout status deployment/library-deployment


Step 20: Demonstrate rollback.
kubectl rollout undo deployment/library-deployment


Expected Output:
- Java application packaged into a Docker image.
- Application executed inside Kubernetes using a Job.
- Kubernetes Deployment, scaling and rollout commands demonstrated separately.
- Pod recreation demonstrated using a Deployment.
Scenario-Based Questions:

1. What happens when one pod crashes?

Answer: Kubernetes detects the failed pod. The Deployment controller creates another pod to maintain the desired replica count.

2. How does Kubernetes maintain the desired number of replicas?

Answer: The Deployment controller continuously compares the actual number of pods with the desired number and creates replacement pods when required.

3. What is the difference between manual scaling and auto scaling?

Answer:
- Manual scaling: Administrator changes the replica count.
- Auto scaling: Kubernetes adjusts replicas automatically based on configured metrics, such as CPU utilization, using Horizontal Pod Autoscaler.
4. Why is a Kubernetes Service required?

Answer:
- Provides a stable network endpoint.
- Allows users to access application pods.
- Distributes traffic across matching pods.
- Keeps application access stable when pods are replaced.
5. How can you recover from a failed application update?

Answer: Use the rollback command.
kubectl rollout undo deployment/library-deployment

Part 2 – Scenario-Based Questions and Answers
Q1(a) Docker – Multi-Container Application
1. What happens if the MySQL container stops while students are accessing the AI-OLMS portal?
- The AI-OLMS application container may continue running.
- Database operations such as login, course retrieval and enrolment may fail.
- Students may experience errors or failed requests.
- Restart MySQL:
docker start aiolms-mysql


- Check its logs:
docker logs aiolms-mysql


2. How can you preserve student and course information even after deleting the MySQL container?

Use a Docker named volume.
-v aiolms-data:/var/lib/mysql


The volume stores database data independently of the container. Even if the container is deleted, the data remains in the volume.

3. Why should AI-OLMS and MySQL run in separate containers?
- Independent deployment.
- Easier maintenance.
- Better isolation.
- Independent scaling.
- Easier database backup and recovery.
- Application and database can use different images and configurations.
4. How can you protect student login credentials and course information from unauthorized access?
- Use strong database passwords.
- Implement authentication and authorization.
- Use HTTPS to encrypt communication.
- Restrict database network access.
- Do not expose the MySQL port publicly.
- Store passwords securely using hashing.
- Avoid hardcoding database credentials in source code.
5. How would you troubleshoot the application if it cannot connect to MySQL?

Check whether both containers are running:
docker ps


Check MySQL logs:
docker logs aiolms-mysql


Check application logs:
docker logs aiolms-app


Check network:
docker network inspect aiolms-network


Verify:
- Both containers belong to the same Docker network.
- The JDBC hostname is aiolms-mysql, not localhost.
- Database name and credentials are correct.
- MySQL is ready to accept connections.
- The application has the correct MySQL JDBC driver and configuration.

Q1(c) System Monitoring using Nagios
1. How can Nagios identify whether the AI-OLMS application server is running or down?

Nagios performs host availability checks.
- If the server responds, it can report the host as UP.
- If the server does not respond, it can report the host as DOWN.
2. What is the difference between WARNING and CRITICAL alerts?
WARNING	CRITICAL
Indicates a potential problem	Indicates a serious problem
Resource may be nearing a limit	Resource may have crossed a critical limit
Requires attention	Requires immediate action

Example: CPU usage may trigger WARNING at a configured threshold and CRITICAL at a higher threshold.

3. What happens if CPU usage reaches 100% when many students access the portal?
- Application response becomes slow.
- Requests may time out.
- Students may face login or examination problems.
- Server performance decreases.
- Nagios can generate a CRITICAL alert.
- The administrator can investigate processes or increase server capacity.
4. How can Nagios detect application failure even when the server is running?

Nagios can use HTTP service monitoring.

For example:
- Server is running.
- Tomcat has stopped.
- HTTP check fails.
- Nagios reports the application service as CRITICAL.
This helps distinguish server availability from application availability.

5. How can an administrator identify whether a problem is caused by Tomcat, MySQL or the server?

Configure separate monitoring checks:
Component	Monitoring check
Server	Host availability
Tomcat	HTTP and process checks
MySQL	MySQL service check

Compare the monitoring results and inspect the logs to identify the failing component.

Q1(d) Container Scaling using Kubernetes
1. What happens if one AI-OLMS application pod crashes during an online examination?
- Kubernetes detects the failed pod.
- The Deployment controller attempts to create a replacement.
- The desired number of replicas is maintained.
- The application can continue serving requests through healthy pods.
However, an interrupted examination submission may still need application-level recovery and database transaction handling.

2. How does Kubernetes maintain the desired number of application replicas?

Kubernetes uses a Deployment controller.

For example, if the desired number is four but only three pods are running, Kubernetes creates another pod.

Command:
kubectl get pods


3. What is the difference between scaling up and scaling down?
- Scaling up increases the number of application instances.
- Scaling down decreases the number of application instances.
Scale up:
kubectl scale deployment aiolms-deployment --replicas=4


Scale down:
kubectl scale deployment aiolms-deployment --replicas=2


4. How can increasing application replicas improve performance during online examinations?
- More application instances can process requests.
- Workload is distributed across multiple pods.
- Individual pods may experience less load.
- Application capacity increases during peak periods.
- The chance of one instance becoming a bottleneck can be reduced.
5. How does a Kubernetes Service distribute incoming requests among multiple application pods?
- A Service selects pods using labels.
- It provides a stable network endpoint.
- It distributes connections among available pod endpoints.
- If one pod becomes unavailable, it can stop receiving new traffic through the Service once its endpoint is removed.
